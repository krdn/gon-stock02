# 모의 주문 장부 운영

KRX 모의 지정가 주문 의도, 제출 응답, 체결·취소 대조를 SQLite에 저장한다. `intent`는 논리적인 주문 한 건의 고유 이름이다. 같은 이름은 재시작해도 다시 전송하지 않는다. [설계](../plans/paper-order-ledger-2026-11.md) · [공식 계약 조사](../research/kis-order-contract-2026-11.md) · [Issue #5](https://github.com/krdn/gon-stock02/issues/5)

## 지금 실행할 수 있는 확인

저장소 루트에서 실행한다. 이 명령은 주문·취소를 전송하지 않는다. 모의 자격증명은 기존 OS 인증 저장소에서 읽는다.

```sh
uv sync --locked
uv run gs02 order-check --output .local/order-check.json
uv run python -m unittest discover -s tests -v
```

`consistent=true`는 조회 시점의 장부·계좌 수량 일치다. 접수·체결·취소 성공이나 수익성 통과가 아니다. 조회 실패·외부 주문·잔고 차이는 종료코드 1과 정제된 사유로 남는다. 계좌번호·토큰·금액·브로커 주문번호는 공개 보고서에서 제외한다.

장부는 `~/.local/state/gon-stock02/<모의계좌 해시>/orders.sqlite3`에 있다. 디렉터리는 0700, DB는 0600이다. 계좌별 파일 잠금으로 한 실행만 장부를 다룬다. REST 호출은 같은 사용자·호스트·계좌의 이 클라이언트끼리 최소 1.1초 간격을 공유한다. 테스트용 `state_root`를 실제 운용에서 변경하면 장부와 호출 큐가 분리되므로 기본 위치를 사용한다.

초기 계좌는 당일 주문과 보유종목이 없어야 한다. 기존 사용자의 주문·보유분을 자동으로 가져오거나 취소하지 않는다. 다른 프로그램·호스트·수동 매매와의 공통 잠금은 제공하지 않는다.

## 상태와 복구

예를 들어 2주 중 1주가 체결된 뒤 취소 응답을 받아도 보유는 1주다. 원주문의 체결 1·취소확인 1·잔량 0과 계좌 1주가 일치해야 `CANCELED`로 확정한다. 이 예시는 합성 테스트이며 실제 체결 증거가 아니다.

| 상태/사유 | 처리 |
|---|---|
| `SUBMITTING` | DB 커밋 뒤 해당 실행에서만 신규 POST 한 번. 재시작하면 `UNKNOWN`. |
| `OPEN`, `PARTIAL` | 접수 또는 부분체결. 다른 새 주문은 기존 주문 종료까지 차단. |
| `CANCEL_SUBMITTING`, `CANCEL_PENDING` | 취소 시도는 한 번만 전송. 접수 응답만으로 예약을 해제하지 않음. |
| `UNKNOWN`, `unknown_submission` | 조회만 수행. 주문번호 없는 응답 불명은 자동 연결·재전송하지 않음. |
| `FILLED`, `CANCELED`, `REJECTED` | 동일 의도 재제출 금지. 부분체결 뒤 취소/거부여도 확인된 보유분은 유지. |
| `balance_mismatch`, `external_order`, `order_quantity_regression` | 대조 전체를 커밋하지 않고 `blocked_reason` 저장. 새 제출 차단. |

통신 실패 뒤에는 위 `order-check`를 다시 실행한다. 조회에 없다는 이유로 새 의도 ID를 만들어 재주문하지 않는다. 주문번호가 없는 불명 상태는 KIS 화면과 실제 기록을 수동 조사해야 한다. 자동으로 불명을 해제하는 명령은 없다. DB를 삭제하거나 상태를 직접 고쳐 우회하지 않는다.

백업은 실행을 종료한 뒤 SQLite backup API 또는 일관된 파일 복사로 수행한다. 코드 롤백 시에도 장부를 보존한다. 다른 계좌로 복사한 DB는 계좌 식별자 검사에서 차단한다. 일별 조회는 시작일부터 최대 89일 간격이며, 그 범위를 넘으면 차단한다. 장기 이력 보관·압축은 후속 작업이다.

## 장중 계약 점검

자동 주문 설정은 `config/paper.json`에서 계속 꺼져 있다. CLI는 조회만 제공한다. 제출·취소는 `OrderService.submit()`·`cancel()` 라이브러리 경로로 구현했다. 자동 전략·청산 스케줄·실계좌 경로는 없다.

1. 해당 날짜의 공식 개장일·특별개장 시각을 확인한다. 확인한 시간대와 출처 URL을 `session` 기록으로 준비한다. 자동 달력 수집기는 아직 없다.
2. 전용 모의계좌에서 `order-check`가 일치하는지 확인한다. 로컬 점검용 정책 사본만 명시적으로 활성화한다. 저장소 기본 설정은 유지한다.
3. KRX 피드에서 검증한 최신 틱을 사용한다. `session`은 `opens_at`, `closes_at`, `checked_at`의 시간대 포함 ISO 문자열과 `source` HTTPS URL을 받는다. 당일 09:00~15:20 안의 확인된 구간, 최근 24시간 확인 기록만 허용한다. URL 존재·내용의 진실성은 코드가 검증하지 않는다.
4. 고유 의도 ID로 1주를 제출한다. `submit`에는 종목·매매방향·수량·지정가·손절 기준·주당 비용·틱·세션을 전달한다. 신규 매수는 계좌 대조와 위험 한도를 통과해야 한다. 대기 후 전송 직전에도 틱·세션을 다시 검사한다.
5. 같은 ID로 다시 호출하고 추가 주문이 없는지 확인한다. `reconcile()`로 원주문과 잔고를 대조한다. 미체결이면 `cancel(intent)`를 한 번 호출하고 대조를 반복한다. 먼저 체결되었다면 실제 체결로 기록하며 취소 성공으로 표시하지 않는다.
6. 매도는 장부의 확인된 보유수량과 브로커 주문가능수량 중 작은 값 이하만 허용한다. 청산 후 0주와 종료 상태를 대조한다. 불명·불일치가 있으면 추가 주문을 중단한다.

신규 주문은 위 세션 입력이 없으면 차단한다. 휴장일·특별개장 여부는 호출자가 공식 자료로 확인해야 한다. 일반 시간표를 매일 복사하는 자동화는 아직 연결하지 않는다. 취소는 신규 매수 활성화와 별개로 알려진 당일 원주문의 잔량에만 요청할 수 있다.

가상 운용자산은 초기 가상금에 모의계좌 총평가액의 기준 대비 증감을 더해 계산한다. 현금 상한은 예수금·D+2 정산금·가상 잔여자금의 최솟값을 사용한다. 기준 이후 입출금·계좌 리셋은 지원하지 않는다. 전용 계좌의 자금 기준이 바뀌면 중단하고 대조해야 한다. 손절 기준은 위험 계산 입력이며 자동 손절 실행을 뜻하지 않는다.

## 검증 범위

2026-11-13 로컬 전체 60개 테스트 통과. 실제 SQLite를 사용해 중복 제출·재시작·응답 불명·취소 경합·매수/매도 수량·계좌 불일치·페이지 처리·세션/시세 만료를 검사했다. 별도 프로세스로 장부 잠금과 1.1초 호출 간격을 확인했다. 네트워크 응답은 합성 fixture다.

실제 모의계좌는 신규 프로세스 두 번에서 빈 주문·빈 보유 장부와 일치했다. [조회 증거](../evidence/paper-order-ledger-2026-11-13.json). 실제 주문은 0건이다. 신 TR의 전량취소 0/0 요청, 실제 부분체결·취소행 갱신, 장중 수신 지연은 미검증이다. 모의 응답이 합성 수량식과 다르면 성공으로 맞추지 않고 차단한 뒤 계약을 수정한다.
