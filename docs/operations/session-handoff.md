# 단계 완료 후 새 세션으로 자동 진행

현재 Codex 앱에서는 AI가 `mcp__codex_tui__create_thread`로 새 작업 세션을 만들고 바로 실행할 수 있다. 사용자가 단계별 자동 진행을 요청한 범위에서 이 기능을 쓴다. Evolve나 별도 CLI 실행기는 필요하지 않다. 앱에 이 도구가 없는 환경에서는 같은 동작을 보장하지 않는다.

전체 기능·의존관계·완료 조건을 먼저 정하고 GitHub Issues와 작업별 문서에 저장한다. 세부 설계는 해당 단계에서 확정한다. 한 단계 안의 조사·수정에는 현재 세션과 필요 시 `/compact`를 사용하고, 검증된 단계 경계에서 새 세션으로 넘어간다. 토큰 절감률은 아직 측정하지 않았다. 새 세션에도 공통 지침·도구 정의·메모리 주입 비용이 든다.

조정 AI는 현재 사용자의 요청·위임 범위를 근거로 이슈 댓글에 `authorization` 기록을 한 번 저장한다. 원래 요청의 출처, 유한한 단계 ID 목록, 완료 조건, 마지막 단계, 제외 범위와 단일 전환 담당 세션 ID를 명시하고 댓글 URL을 작업 파일에 고정한다. 이미 위임받은 범위는 반복 승인받지 않는다. 후속 세션이 이 목록을 임의로 늘리거나 완료 조건을 낮출 수 없으며, 범위 변경은 사용자의 추가 지시를 기록한 뒤에만 반영한다.

전환 담당은 authorization의 최초 세션에서 시작해 유효한 `started` 댓글의 `next_thread_id`로만 승계된다. 이전 담당은 승계 후 추가 생성 권한을 갖지 않는다. 실패 세션의 재개 조정은 원래 사용자의 요청을 받은 세션이나 사용자가 지정한 조정 세션이 맡으며, 살아 있는 조정 세션이 없으면 자동 복구를 가정하지 않는다.

## 전환 순서

1. 현재 단계의 수용 기준을 검사한다. 필요한 리뷰·PR·CI를 마치고 저장소의 정상 절차로 반영한다. 테스트 종료코드만으로 미실행 기능을 완료 처리하지 않는다.
2. `docs/tasks/`의 해당 작업 파일에 목표·범위, 완료/미완료, 검증 근거, 실패한 시도, 다음 단계와 필수 읽기 목록을 짧게 기록한다. `docs/STATE.md`에는 현재 작업과 다음 작업의 링크만 갱신한다. 반영된 브랜치/SHA와 인계 파일의 Git blob ID, 기존 별도 미커밋 변경 목록을 확인한다. 원격 커밋·이슈·PR/CI와 내용을 대조한다.
3. 다음 단계가 고정된 `authorization` 댓글의 목록에 있고 차단되지 않았는지 확인한다. 전환 상태의 기준은 **해당 이슈의 전환 댓글들** 한 곳이다. 매번 같은 `transition_id`(작업 번호와 단계)의 기존 기록과 앱 세션을 먼저 조회한다. 기록이 없음을 확인한 지정 담당 세션만 `dispatch=pending`, `next_task`, 기준 SHA·인계 blob ID·기존 별도 변경 목록·authorization URL을 댓글에 저장하고 원격 조회로 확인한다. 작업 문서에는 전환 ID와 기준 이슈 URL을 2단계에서 미리 적어 두며, 댓글 생성 후 기준 커밋을 다시 수정하지 않는다. 전체 대화나 과거 로그를 인계하지 않는다.
4. 현재 제공되는 도구를 확인하고 `create_thread`를 **한 번** 호출한다. 제목에 전환 ID를 넣고, 프롬프트에는 작업 파일의 절대 경로와 수행 범위·종료 조건을 전달한다. 프롬프트는 UTF-8 1,000바이트 이내다. 기본 모델을 상속하며 모델을 임의로 교체하지 않는다.
5. 실제 반환된 새 세션 ID와 `dispatch=started`를 같은 전환 ID의 후속 이슈 댓글에 기록하고 원격 조회로 확인한다. 생성 이후 부모는 공유 파일 변경·Git index 조작을 끝내고 댓글 기록만 마친 뒤 종료한다. 댓글 저장 실패 시 반환 ID를 로컬 증거와 최종 응답에 보존하고 같은 작업을 재생성하지 않는다. 새 세션은 최신 유효 started 댓글의 ID가 자신의 ID와 일치하기 전에는 구현하지 않는다. `CODEX_THREAD_ID`가 제공되면 이를 앱의 `read_thread` 결과와 대조한다. 자기 ID를 확인할 수 없으면 추정하지 않는다. started가 아직 없으면 5초 간격으로 최대 3회 재조회하고, 계속 확인되지 않으면 대기 상태를 남기고 종료한다. 부모는 started 기록 후 대기 종료를 확인한 경우 같은 세션에 재개 지시를 보낼 수 있다.
6. 새 세션은 AGENTS → WORKFLOW/STATE → 지정 작업 → 필수 자료 순으로 읽는다. authorization과 전환 댓글, 원격 상태, 기준 HEAD·인계 blob ID·기존 별도 변경 목록을 대조한다. 불일치는 구현 전 중단한다. 같은 방식으로 다음 단계에 넘기며 승인된 마지막 단계에서 멈춘다.

새 세션 생성은 작업 폴더 이동과 다르다. 이 도구는 호출 세션의 작업 폴더를 상속한다. 순차 작업은 현재 checkout을 이어 쓰며, 병렬 수정이나 격리가 필요할 때만 별도 worktree를 준비한다. worktree 자체는 보안 격리나 컨텍스트 초기화를 제공하지 않는다.

## 실패와 재개

- 검사 실패·필수 입력 부재·사용자 중지·다음 작업 차단 시 다음 세션을 생성하지 않는다. 실패 이유와 재개 조건을 작업 파일에 남긴다.
- 원인에 관계없이 기존 `pending` 또는 `started` 기록이 있으면 새 생성 전에 `list_threads`와 `read_thread`에서 전환 ID·작업 경로·실제 실행 상태를 확인한다. 존재하는 작업을 다시 만들지 않는다. 존재 여부를 확정할 수 없으면 자동 재시도하지 않는다. 단일 부모의 생성/기록 사이 장애와 여러 부모의 동시 실행 모두 트랜잭션 수준의 정확히 한 번 실행을 보장하지 않으며 이 복구 절차는 미실증이다.
- 기본 재개는 지정 조정 AI가 실패 원인 해소를 기존 수용 기준으로 확인하고, 실패 세션과 그 작업 프로세스가 중단됐는지 확인한 뒤 그 세션에 명시적인 재개 지시를 보내는 방식이다. 완료 단계를 다시 실행하지 않는다. 새 세션으로 대체하는 경로는 미실증이며 기존 세션 idle·잔존 프로세스 종료·기준 HEAD·인계 해시·기존 별도 변경 목록 일치를 확인한 경우에만 선택한다. 실패 후 남은 미커밋 결과는 먼저 검토·정리해서 기록하며 몰래 버리거나 완료로 간주하지 않는다.
- 대체 세션을 선택할 때는 기존 ID의 폐기(`superseded`)를 먼저 이슈에 기록한다. 같은 전환 ID에서는 최신 유효 started만 권한을 가지며 폐기된 세션은 다시 실행하지 않는다.
- 수용 기준을 낮추거나 실패 검사를 끄는 것은 원인 해소가 아니다. 합성 시험의 gate 변경은 처음부터 승인된 시험 단계였다. 실제 작업에서 이런 변경이 사용자 위임 범위를 벗어나면 추가 지시가 필요하다.
- 앱/호스트 종료·재부팅·네트워크 단절 후 무인 복구는 이번 범위에서 검증하지 않았다. 새 세션을 만드는 기능과 상시 실행 스케줄러는 별개다.

## 인계 문서 최소 항목

```text
작업/단계 및 authorization 댓글 URL:
기준 이슈·브랜치·SHA·PR/CI:
완료와 실제 검증:
미완료·차단·실패:
다음 작업 파일 / 필수 읽기 / 완료 조건:
transition_id / 기준 이슈 URL (전환 댓글에서 dispatch·실제 next_thread_id 조회):
마지막 허용 단계·중지 조건:
```

claude-mem은 이전 결정·실패를 찾는 보조 수단이다. 작업 상태의 기준은 GitHub의 문서·이슈·코드·검사 결과다. 새 세션에서 전체 메모리나 대화를 다시 읽지 않는다. 합성 검증과 적용 상태는 [Issue #16 작업 기록](../tasks/16-native-session-handoff.md)에 남긴다.
